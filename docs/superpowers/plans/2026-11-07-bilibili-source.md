# Bilibili 音源接入计划

日期：2026-11-07。基线：`a4296ff`（搜索栏和空结果展示已提交，1130 项测试、格式检查、严格 Clippy 和 Linux 构建通过）。

2026-11-11 显示规则更新：用户要求按子项名称显示歌名。多 P 曲目以当前分 P 的名称为主标题，空名称回退视频标题；单页 BV 优先使用视频详情中按 BV 匹配的合集条目标题，缺失时沿用视频标题。视频和合集名称保留为辅助信息，只有多 P 才显示 `Pn/N`；旧队列和历史加载时转换标题，播放身份仍为 `bvid + cid`。本条覆盖下文首版方案中“视频标题为主、分 P 名称仅辅助”的旧规则，合集独立浏览入口仍属后续范围。

## 1. 目标和首版范围

把 Bilibili 作为可切换的独立音源，复用应用现有的队列、播放控制、EQ、响度控制、播放历史、托盘和系统媒体会话。播放的是视频中可访问的音频流，内容身份保留视频和分 P 信息。

2026-11-07 用户明确的播放与展示规则：**只请求独立音频流，曲目标题沿用视频标题**。首版以音视频分离的 DASH 音轨接入为目标，音频工作线程接收选中的音频资源。

2026-11-07 方案访谈确认：**首版支持 Bilibili 账号登录，采用应用内二维码 + B 站 App 扫码确认**。登录不再属于后续范围；二维码流程先验证接口与完整授权生命周期，再接入应用。用户随后要求先核实音频档位与视频分辨率的关系，未选择“只播放无损”的限制；默认选择当前权限下可解码的最佳音轨。

2026-11-07 入口访谈确认：**先播放已登录账号自己的收藏夹**。用户也希望未来播放 B 站合集；首版先围绕个人收藏夹完成浏览到连续播放的流程，合集及搜索/链接入口放入后续扩展。登录交互已选择扫码；用户选择批量播放时**展开全部分 P，按收藏夹中的视频顺序、各视频内的分 P 顺序连续播放**。

2026-11-07 来源切换访谈确认：**切换音源浏览时保持当前音乐播放，直到在另一音源成功点播歌曲才切换播放来源**。浏览来源和播放来源分别管理，切换浏览不能清空正在播放的队列、取消当前音源的预加载或把其后续请求发给新浏览音源。

首版范围如下：

- 应用内展示登录二维码，用户用 B 站 App 扫码并确认；访问账号有权使用且允许第三方客户端使用的内容，按实际权限获取独立音轨。
- 读取已登录账号自己的收藏夹，展示收藏夹列表及其中的视频，支持分页、刷新和加载失败重试。
- 收藏夹内的视频加载标题、UP 主、封面、时长和分 P；首版按只读浏览与播放规划，收藏夹编辑另行扩展。
- 多 P 视频先展示分 P 列表，支持播放单个分 P、播放下一首和加入队列。
- 收藏夹支持播放全部、选择条目播放和加入队列；批量操作展开选中视频的全部分 P，按视频顺序、分 P 顺序生成队列，每个分 P 使用独立的 bvid + cid 身份。
- 播放、暂停、上一首、下一首、跳转、顺序/循环/随机播放、音量、EQ、播放历史和媒体会话。
- 展示实际获得的音频编码和码率，默认选择当前权限下可解码的最佳音频流。
- 视频标题作为曲目主标题；多 P 内容的分 P 序号和名称作为辅助信息，保留视频标题。
- 从音源选择入口切换 OpenSubsonic/Bilibili；第一版每个队列只属于一个音源。
- 浏览来源与播放来源独立；切换浏览保持播放，成功准备并接受另一个音源的点播后再提交新的播放来源及队列。

后续范围：B 站合集、关键词搜索、视频链接/BV 输入入口、其他账号的公开收藏夹、收藏夹编辑、UP 主主页、本地 Bilibili 收藏、混合音源队列和跨音源搜索。第一版不实现视频画面、弹幕、直播或永久下载管理。

**音质定义：** 视频的 1080P/4K 等清晰度不代表音频无损。界面根据实际音频流显示 AAC/FLAC 等编码及可确认的码率、采样率、声道数；没有可靠数据时显示未知，不依据标题中的“Hi-Res”“无损”作判断。FLAC 等高质量音轨是否可用，取决于内容、账号权限、访问方式和解码器能力，不能预先保证。

### 2026-11-08 应用基础批次

已写入来源身份、能力、配置迁移、OpenSubsonic 适配和 HTTP 资源边界，尚未启用 Bilibili Provider 或登录/收藏夹界面。

- `SourceProfile::OpenSubsonic` 引用现有 `servers` 的 ID，不复制密码；Bilibili 配置只保留账号元数据与凭据引用。旧配置迁移可重复运行，Bilibili-only 配置不会创建虚构服务器；损坏来源条目不会丢弃有效旧配置。
- 主应用、推荐和导入改用 `MusicSource`；已有 Subsonic 协议实现继续复用。来源适配器为歌曲补齐 `SourceId`，远端 `Song.id` 保持原值。混合来源的替换/追加队列在发送播放命令前拒绝。
- 会话保存来源身份，旧 OpenSubsonic 会话按当前来源补齐身份并保留重复条目；恢复拒绝其他来源或混合来源队列。历史更新按来源与远端 ID 匹配。
- 会话、历史、响度的后台写入与清理按 Provider 和来源隔离；新来源使用独立子目录，不能采用旧全局缓存。OpenSubsonic JSON 和封面保留原路径，封面加载使用请求音源的身份，通知使用播放会话身份。
- `PlaybackResource` 包含媒体/表示身份、HTTP 请求头、音质、时长、有效期和备用地址。资源不可序列化，调试输出隐藏 URL、请求头及代理凭据；音频缓存键包含来源和表示，不使用签名 URL。原先按地址构造的 OpenSubsonic 音频缓存键不能证明账号归属，升级后可能需要重新拉取音频，旧文件按既有缓存上限淘汰。
- 播放、预加载、Gapless 后的跳转和重试保留逐资源请求头与缓存策略。带自定义头的资源仅允许同域跳转，并关闭 reqwest 自动改写 Referer；不修改共享客户端默认头或系统代理。
- 临时音频缓存使用每个读取器独立、受字节上限约束的临时文件，读取器关闭后释放，不发布永久 `.audio` 文件；超过缓存上限仍可 Range 读取和跳转。

## 3. 实施原则

1. 用户已将 Bilibili 指定为下一项功能，实施优先级相应调整；仍保留 #28 的音源抽象和 #38 的可行性验证。
2. 先交付计划，再完成接口验证；只有证据满足条件后才接入 Bilibili 播放功能。音源抽象可以独立推进。
3. 不把 Bilibili 判断插入 Subsonic 的 URL 构造函数，不修改 Subsonic 协议，不建立伪 Subsonic 代理。
4. 每个阶段保持应用可编译、现有 OpenSubsonic 功能可用；架构迁移与可见功能分别形成可评审的改动。
5. 当前工作在已有工作区进行；除非用户再次要求，不自动提交、推送或改变分支。
6. 音源接口只获取事实数据，排序、队列状态、播放历史和输出设备仍由现有领域模块负责。
7. 不把短期播放 URL、Cookie、令牌写入播放会话、普通配置或日志；错误输出也需去除敏感资源地址。
8. 不绕过登录、付费、区域、DRM 或访问控制。访问失败按实际原因反馈。

## 4. 目标架构

```text
音源选择、搜索、详情页、歌曲行
                 |
        MusicSource + SourceCapabilities
             /               \
 OpenSubsonicAdapter     BilibiliProvider
             \               /
       MediaKey + 可取消的资源解析
                 |
      PlaybackResource / ArtworkResource
                 |
       现有播放状态、音频工作线程
                 |
      HTTP / Rodio / EQ / 输出设备
```

### 4.1 身份与配置

- `ProviderKind`：`OpenSubsonic`、`Bilibili`。
- `SourceId`：稳定的来源身份，不从显示名称、播放 URL 或当前登录 Cookie 推导。
- `BrowsingSourceId` 与 `PlaybackSourceId`：分别表示页面查询归属和当前播放归属；浏览切换不会改变播放归属。页面请求的 generation 与播放请求的 generation 分开校验。
- `MediaKey`：`SourceId + remote_id`。Bilibili 远端身份使用规范化 `bvid + cid`；`p` 是页面序号，不能用它替代 `cid`。
- `SourceProfile`：按 Provider 区分配置。过渡实现中 OpenSubsonic 只引用既有 `ServerProfile.id`，地址/账号/密码继续保存在原服务器条目中，避免重复迁移凭据；Bilibili 保存稳定 ID、显示名、账号 ID 和凭据引用，使用独立授权入口。
- 先保留 `Song.id` 的远端 ID 语义和旧 Subsonic JSON 解析；来源身份在统一媒体、队列、会话与历史边界补齐，不把来源前缀发送给 Subsonic API。
- 新配置字段带 serde 默认值；旧配置中的服务器转换为 OpenSubsonic 来源。迁移必须可重复运行且不改变已有服务器 ID。
- 迁移期间保留旧服务器配置字段的兼容读取与镜像写入；只在 OpenSubsonic 来源激活时更新服务器镜像。
- 旧 OpenSubsonic 会话和缓存继续读取原来的服务器目录；新来源使用独立目录，不能通过简单去除标点得到可能碰撞的目录名。

### 4.2 音源接口

新增 `src/source.rs` 和 `src/source/`。第一版采用编译期 Provider 与统一分派，不引入插件运行时。

统一接口覆盖：

- 来源展示信息和能力查询。
- 搜索、媒体详情、分组浏览、封面和歌词查询。
- 收藏、歌单读写与播放报告；不支持时由能力模型隐藏或禁用入口。
- 异步解析可播放资源与音质信息。
- 认证、网络、限流、资源不可用、格式、权限和本地 I/O 错误的统一分类。

可以使用集中分派的 `MusicSource` 枚举避免引入仅为异步 trait 服务的新依赖。具体 Provider 分支集中在音源层，页面通过能力与展示模型工作。

Bilibili 的 UP 主不等同于歌曲的实际演唱者。详情和搜索展示应标明“UP 主”和分 P，不能从上传者信息生成虚假的艺术家或专辑详情。来源不支持专辑、艺术家、Subsonic 收藏写入和 Scrobble 时，不展示这些操作。

### 4.3 视频元数据与独立音轨的映射

| 应用信息 | Bilibili 来源 | 规则 |
| --- | --- | --- |
| 曲目主标题 | 视频详情的 `title` | 搜索结果、播放条、队列、历史与系统媒体会话沿用视频标题，不从标题猜测或重写歌名 |
| 封面 | 视频封面 | 封面图片独立加载 |
| 创作者 | 视频 UP 主信息 | 标明上传者身份，不推断实际演唱者 |
| 分 P 辅助信息 | 分 P 序号、分 P 名称 | 多 P 时显示在辅助文字中，不替换曲目主标题 |
| 播放身份 | 规范化 `bvid + cid` | 分 P 名称、视频标题变化不改变对应媒体身份 |
| 时长 | 当前分 P 的时长及解码结果 | 播放进度使用当前分 P 时长，多 P 时不误用整个视频的总时长 |
| 播放资源 | 当前 cid 的独立音轨 | 从 `dash.audio` 及实测支持的独立音轨分组选择，不把 `dash.video` 交给播放器 |

视频元数据查询和音轨解析分开：搜索或详情取得标题、封面和分 P；播放前按选中的 cid 解析音轨，再请求音频 CDN 资源。第一版不加入视频下载、音视频合并、从复用的视频流提取音频或 FFmpeg 转换路径。

如果内容未提供当前实现可支持的独立音轨，明确报告音轨不可用或格式不支持。不能因为用户说明常见视频采用音视频分离，就把所有视频、账号和接口响应都视为已经验证。

### 4.4 播放资源和缓存

`PlaybackResource` 必须表达：

- 稳定媒体身份与实际音频表示身份。
- HTTP 地址与逐资源请求头，未来可扩展本地文件。
- 编码、码率以及可确认的采样率、声道数、时长。
- 可确认的有效期；无法确认时标记未知，不猜测固定时长。
- 缓存策略、稳定缓存键和可用备用地址。

**解析与重试：** 初次播放、恢复会话、预加载和过期重试均通过同一资源解析器。解析任务关联播放来源 generation、队列 occurrence 和媒体身份；切歌、停止、切换播放来源或注销所属账号后，迟到结果不得提交到播放器。仅切换浏览来源不取消当前播放的解析、预加载或重连。

**URL 更新：** 遇到疑似资源过期时按媒体身份重新解析一次，再交给现有有界重连流程。401/403 不能一概解释为 URL 过期；若实际为权限、区域、删除或风控，应终止自动重试并显示相应错误。

**缓存一致性：** 缓存键包含来源、视频、cid 和音频表示，不包含签名 URL。URL 刷新后若编码、表示或长度等验证不一致，放弃旧部分缓存，按歌曲时间位置重新准备，不能拼接不同资源。

**请求头隔离：** 使用逐请求头，不把 Bilibili 的认证或 Referer 设置为共享 HTTP 客户端的全局默认值。重定向需核对认证头的目标域策略，测试认证头不会进入其他音源请求。

**临时缓存：** Bilibili 第一版使用有界临时缓存，来源移除或明确清理时可清除；UI 不增加永久下载入口。OpenSubsonic 已有持久缓存行为保持兼容。

- [x] 切换浏览来源只刷新页面数据，保留当前播放来源、队列及资源解析/预加载/重试。
- [x] 在另一来源点播时先准备新资源；准备失败保留原播放，音频命令接受后才保存旧播放会话、结束旧播放事件并提交新来源与队列。
- [x] 队列页与媒体会话显示正在播放的来源；在另一浏览来源加入队列时更新该来源自己的队列，不混入当前播放队列。
- [x] 队列中保存媒体身份和元数据，重启后重新解析资源，不能依赖上次的临时 URL；浏览来源与播放来源分别恢复。
- [x] 停止、快速切歌、多次跳转、切换播放来源后迟到资源不能改变当前队列或播放状态；切换浏览来源时当前音乐和必要后台请求继续。
- [x] Bilibili 不向 Navidrome 发送正在播放、Scrobble 或收藏写入请求。
- [x] 同名/同 ID 媒体的封面、响度、历史、播放位置与缓存互不污染。
- [ ] 普通播放、循环、随机、自然结束、键盘快捷键、托盘、通知和媒体会话完整接通。
- [x] Gapless 只在已验证可准备下一条资源时启用；资源解析失败时走正常下一首路径。
- [ ] 验证过期刷新、备用地址、限流和网络中断，复用有界重连预算。

通过条件：Bilibili 能连续听歌，切回 OpenSubsonic 后原有曲库和播放状态正常。

## 6. 风险、处理与停止条件

| 风险 | 处理与验收要求 |
| --- | --- |
| 接口适用性或授权范围不明确 | 阶段 0 给出来源和证据；保持播放接入未启用，不声称“公开返回即可正式接入” |
| 已登录账号仍无目标音质 | 根据实际音轨与账号权限选择，音质回退规则由访谈确定，不承诺登录后所有视频都有无损 |
| 授权过期或凭据库不可用 | 明确账号状态与凭据保存结果，不回退普通配置明文保存，注销时取消旧账号播放解析 |
| 接口结构或访问策略变化 | Provider 内集中处理，有界重试和明确错误；其失败不得影响 OpenSubsonic |
| 音频质量与视频清晰度混淆 | 展示真实音轨信息，未知数据不猜测，不承诺每个视频有无损 |
| 短期 URL 过期或表示变化 | 重新解析并验证表示；旧部分缓存不跨表示拼接 |
| 同一 BV 多 P 或分 P 变化 | 身份使用 bvid + cid，页面序号只用于选择；已删除 cid 显示不可用 |
| 快速切歌、跳转或播放来源切换 | 播放 generation + occurrence 校验；取消任务，拒收旧响应；浏览切换只更新页面 generation |
| 来源凭据或缓存混用 | 逐资源请求头、来源命名空间、跨来源回归测试 |
| 音源迁移影响当前功能 | 先只迁移 OpenSubsonic 并跑完整验证，再启用 Bilibili |

## 7. 开始编码的顺序

按 **阶段 0 的验证工具与研究记录 → 阶段 1 的身份/能力/迁移 → 阶段 2 的 OpenSubsonic 适配 → 阶段 2a 的账号授权与凭据 → 阶段 3–5 的 Bilibili 功能 → 阶段 7 的完整验收** 推进。

第一批可评审产物是接口验证记录和兼容迁移设计。第一批应用代码是来源身份、能力模型及 OpenSubsonic 适配，不直接在搜索页或音频线程中添加 Bilibili 特例。

功能完整完成以阶段 2a、阶段 4–5 与阶段 7 的验收为准，首版必须能从已登录账号自己的收藏夹连续播放；仅新增模型、Provider 文件或取得播放 URL 不算 Bilibili 音源已经完成。
