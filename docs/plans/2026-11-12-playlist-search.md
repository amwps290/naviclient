# 歌单内搜索实现方案

日期：2026-11-12。状态：2026-11-24 已接入功能并完成自动化验证，原生窗口与跨平台人工验收待完成。

目标：用户能在包含大量歌曲的歌单中，通过歌名、歌手、专辑或 Bilibili 元数据快速找到歌曲，并准确播放、选择和移除对应条目。

## 实施记录（2026-11-24）

用户确认首版单曲播放从原歌单对应位置开始，后续继续整张歌单；不将搜索结果
自动替换为播放队列。以下实施记录优先于下文保留的实现前方案。

- 普通歌单和 Bilibili 收藏夹使用同一搜索索引。最新代码采用流式歌单加载，
  因此不再用 `PlaylistLoaded`/`Msg::PlaylistSongs` 整体返回：来源批次先在
  后台建立索引再转交 UI，索引经 `PlaylistIndexed` 在完整加载时接入；
  两侧更新通道均有界，取消标记让已启动的阻塞工作协作退出。
- 查询按约 100ms 合并后后台匹配，不发网络请求。结果借用原歌曲切片与共享
  位置索引，保持原顺序、原序号和重复条目；同一歌曲的不同出现位置不去重。
  单曲与菜单从原位置播放完整歌单，顶部全部播放/追加不受筛选影响，批量动作
  只处理匹配结果中的选择。
- 放大镜固定在刷新按钮旁，点击图标或 Ctrl+F 在同一操作栏向右展开输入框，
  向左收回，保留横向通道避免展开时挪动图标或歌曲列表；使用框架的有状态
  spring 保留中断后的位置/速度并遵守减少动态效果设置。数量/错误重试复用现有
  状态行，不在下方另开输入栏。点击 × 或再次点击图标收起并清空筛选；第一次
  Esc 清空，空查询时 Esc 收起并回到列表。按全库搜索参考截图统一为一体胶囊：
  放大镜、透明 Input 和关闭按钮共享背景，未聚焦不显示独立输入框边线；聚焦
  使用胶囊同层内边框，并监听 Focus/Blur 更新颜色，避免矩形裁剪外扩光圈。
  歌单操作栏使用完整可用宽度，搜索在保留紧凑高度的同时展开到右侧可用空间。
  未全局禁用其他输入框的焦点样式。真实 GPUI 控件/绘制
  primitive 测试覆盖固定锚点、窄布局、输入文字、Enter、Ctrl+A、Esc、Tab、
  浅/深主题焦点边框；动画配置使用确定性时间步测试，实际动画观感仍待实机。
  列表焦点显式注册为 Tab stop，未增加阻断普通按键传播的包装层。
- 搜索条件变化清理歌单选择并使旧行/菜单失效；清除恢复最近定位条目或之前
  的滚动行。切换来源/歌单重置查询和任务；刷新保留关键词并重新筛选。
  刷新失败仍沿用既有流式加载语义：保留可用旧内容/已收到预览并显示重试，
  不将不完整新列表当成完整可搜索歌单，也不额外引入完整快照回滚。
- 删除菜单捕获完整歌单顺序和原始位置，确认提交前再次验证视图归属；非空
  查询禁用排序。查询不写配置或播放会话。README、产品规划和开发计划已同步。

## 1. 已确定的产品行为

首版在歌单详情页加入本地即时搜索。搜索范围为当前音乐源、当前歌单中已完成加载的全部可用条目。Navidrome/OpenSubsonic 歌单与 Bilibili 收藏夹采用同一套筛选逻辑。

| 决策 | 首版行为 |
| --- | --- |
| 查询方式 | 输入后即时筛选，约 100 ms 合并连续输入；搜索不发出网络请求 |
| 匹配字段 | 歌名、歌手、专辑；Bilibili 额外包含 UP 主、视频标题、分 P 标题和合集标题 |
| 结果顺序 | 保持原歌单条目顺序，重复歌曲分别保留 |
| 行号 | 显示原歌单序号，筛选后可以出现 3、128、256 等不连续序号 |
| 单曲播放 | 从该条目在原歌单的位置开始，播放队列包含整张歌单 |
| 批量操作 | 只处理当前结果中选中的条目；Ctrl+A 全选当前匹配结果 |
| 顶部全部操作 | “全部播放”“全部加入”始终处理整张歌单 |
| 歌单编辑 | 搜索结果允许移除对应条目；排序调整需要先清除搜索 |
| 持久化 | 搜索状态保存在当前会话内，不写入配置或播放会话文件 |

拼音、首字母、错别字容错、按字段表达式、相关度排序与其他列表内搜索作为后续扩展。首版无需新的服务端 API 或依赖。

## 3. 界面与交互

### 3.1 搜索条

搜索条位于歌单头部下方、歌曲表头上方，与现有加载/编辑提示共同处于固定区域；歌曲列表独立滚动。

```text
歌单名                                      1860 首
[全部播放] [全部加入] [重命名] [删除] [刷新]

[⌕ 搜索歌名、歌手、专辑…                 ×]   12 / 1860 首
共享歌单 · 仅所有者可编辑

序号    歌名                         歌手       时长
  3     …                            …          …
128     …                            …          …
256     …                            …          …
```

数字仅为布局示例。结果数量以完整详情中的实际可用条目数为分母，不使用可能过期的歌单摘要 `song_count`。Bilibili 按分 P 歌曲条目计数，不能把视频数量当成歌曲数量。

- 普通歌单占位文案：“搜索歌名、歌手、专辑…”；Bilibili 占位文案：“搜索歌曲、UP 主、视频或分 P…”。
- 输入框有可访问名称，清除按钮有独立可访问名称；结果数量采用普通说明文字。
- 窄窗口搜索框占满可用宽度，数量可换到下一行；保留清除按钮，避免挤占歌曲表格操作。
- 关键词为空时显示完整列表和总数；有效条件变化后回到结果顶部。
- 数据可用时顶部“全部播放/加入”的可用性按完整歌单判断，即使当前搜索没有结果也可操作。
- 筛选中的旧结果可暂时保留为弱化展示，显示“筛选中…”，对应行与批量操作暂时不可执行，避免旧行在新条件下被点击。

### 3.2 键盘

| 场景 | 行为 |
| --- | --- |
| 歌单详情页触发搜索动作，默认 Ctrl+F | 聚焦本页搜索框，遵守用户配置的快捷键 |
| 歌单详情页显示队列/历史抽屉时触发搜索动作 | 收起抽屉后聚焦歌单搜索，保留队列内容与队列选择状态 |
| 其他普通浏览页面触发搜索动作 | 保持全库搜索行为 |
| 搜索输入框 Ctrl+A | 选择输入文字，由输入控件处理 |
| 列表获得焦点后 Ctrl+A | 全选当前结果中的所有条目 |
| 搜索框内 Enter | 由输入框和输入法处理确认，不触发播放器动作 |
| 列表获得焦点后 Enter | 有多选时播放所选集合，否则从光标条目在原歌单的位置开始 |
| 搜索框内 Esc，关键词非空 | 清空关键词，保留输入焦点 |
| 搜索框内 Esc，关键词已空 | 将焦点交还歌曲列表 |
| 搜索框外 Esc | 保持现有弹层、菜单、多选、队列和返回行为 |

Tab 按顺序访问输入框、清除按钮与列表；列表继续支持现有 Shift+上下键与 Ctrl/Shift 点击选择。进入列表焦点时可选择首条有效结果，方便继续用键盘操作；无结果时保持无选择。

快捷键录制、活动弹窗、歌曲菜单和设置界面的焦点规则优先。搜索动作的特殊分发仅允许在没有其他输入焦点，或当前焦点正是歌单搜索框时执行；编辑名称、歌词或设置字段时保留输入控件行为。

聚焦歌单搜索时收起队列/历史抽屉，使后续列表选择与播放明确作用于歌单结果。不能让输入焦点位于歌单，而 `active_song_list_scope` 仍指向队列；收起抽屉只改变展示，不清理队列内容和对应作用域的选择。

### 3.3 页面状态

| 状态 | 展示与行为 |
| --- | --- |
| 初次加载详情 | 显示现有加载状态，允许输入关键词，加载完成后应用最新值；不显示“无匹配” |
| 索引构建/筛选中 | 展示忙碌状态，结果数量等待新结果；允许继续修改或清除关键词 |
| 歌单本身为空 | 显示现有空歌单说明，数量为 0 |
| 歌单非空但无匹配 | “没有找到匹配歌曲”，提供清除搜索入口，数量为 `0 / N` |
| 详情加载失败 | 保留实际错误和重试入口，不解释为无匹配 |
| 同一歌单刷新中 | 保留关键词与旧内容，可显示旧内容但暂时禁用条目操作；新详情接受后重新筛选 |
| 刷新失败 | 保留可用的旧快照、关键词与结果，恢复对旧快照的操作能力，显示刷新失败 |
| 歌单编辑中 | 保留关键词，条目操作依照现有编辑状态禁用；编辑刷新完成后重新匹配 |
| 歌单删除或音乐源变化 | 清理对应查询、结果、选择与后台任务 |

## 4. 匹配规则与索引

### 4.1 规范化

查询词与各字段采用一致处理：Unicode NFKC 规范化、转小写、处理前后空白。英文大小写与全角字符因此可以匹配，中文、日文和其他文字字符保留。

查询按 Unicode 空白分词，规范化后去掉空词并去重。每个词都必须在该条目的至少一个字段中以连续子串出现，即“词之间 AND，字段之间 OR”。词可以分别出现在不同字段。

例如 `周杰伦 稻香` 可以分别命中歌手与歌名；`love story` 必须同时命中两个词。字段保持独立，不把字段首尾直接拼成能够产生虚假跨字段命中的字符串。

首版保留标点，不采用歌词严格匹配模块中删除标点的规范化函数。简繁体转换、艺名别名与拼音不自动推断。

### 4.2 索引结构

建议新增纯函数模块 `src/app/playlists/search_index.rs`，提供：

- `PlaylistSearchIndex`：按原歌单顺序保存规范化字段，条目位置与完整歌曲向量位置一一对应。
- `QueryTerms`：规范化并去重后的搜索词，用于比较实际搜索条件是否变化。
- `matching_indices(index, terms, cancellation)`：返回按原始位置升序排列的匹配索引。

索引只保存必要的搜索字段，不保存另一份完整 `Song`。相同歌曲 ID 在位置 0 和 2 出现时，索引仍有两条记录，匹配结果保留 `[0, 2]`。

全量无条件视图使用专门状态表示，无需构造 `0..N` 的索引数组。有条件视图使用共享不可变匹配索引；空索引明确表示一次已完成的无匹配结果。

## 5. 状态模型与异步流程

### 5.1 状态归属

搜索数据状态归属于 `PlaylistLibrary`，输入控件和焦点归属于 `NavidromeApp` 的歌单搜索 UI。建议新增 `search_state.rs` 管理纯状态转换，`search.rs` 管理任务和控件订阅，`search_view.rs` 管理搜索条。

核心状态如下；名称可在实施时依照模块习惯调整，语义必须保留：

| 状态 | 用途 |
| --- | --- |
| `PlaylistIdentity { source, playlist_id }` | 使用完整音乐源身份，避免不同来源同名或同 ID 歌单冲突 |
| `snapshot_id` | 已接受的完整详情版本，可使用对应的 `LibraryRequest`；同歌单刷新也产生新版本 |
| `query`、`terms` | 保存输入文本与实际匹配条件；仅空白/大小写等价编辑可避免重复筛选 |
| `query_revision` | 使更早的筛选结果和行事件失效 |
| `index: Arc<PlaylistSearchIndex>` | 后台筛选复用的不可变字段索引 |
| `projection` | 完整视图或匹配索引视图 |
| `status` | 等待详情、构建/筛选中、结果就绪与内部任务失败 |
| 搜索前的滚动位置 | 清除搜索时恢复浏览上下文 |
| 最近定位的原始条目 | 清除搜索时优先定位到刚选中的歌曲，不按歌曲 ID 去重定位 |
| 任务句柄与取消标记 | 合并输入、取消过时计算以及退出清理 |

任务结果必须同时满足音乐源、歌单 ID、详情快照版本、查询版本与当前实际条件一致，才能被接受。请求/快照版本不能在页面重置后与仍可能返回的旧任务碰撞。

### 5.2 加载与索引构建

1. 保持现有来源 `playlist()` 的完整详情返回语义。
2. 详情加载任务得到 `PlaylistDetails` 后，将其所有权移动到 `spawn_blocking`，在后台构建搜索字段索引；完成后将详情与索引一起返回。
3. 新增应用层 `PlaylistLoaded` 完成数据，供 `Msg::PlaylistSongs` 传递；通过合适的 `pub(crate)` 边界或应用模块重导出供 `msg.rs` 引用。来源层仍使用原 `PlaylistDetails`。
4. 主线程接受数据前先验证现有详情请求归属，再更新完整快照与搜索索引。构建过程中不在主线程克隆整个歌曲向量。
5. 接受新快照后清除该作用域选择，依据最新关键词生成视图。全空查询可以立即显示全部；非空查询进入后台筛选。
6. 构建失败时保留加载失败状态；刷新已有歌单失败时保留旧快照，不接纳半份详情或半份索引。

### 5.3 输入与筛选

1. 输入变化立即同步原文，计算规范化条件。
2. 实际条件未变时保留当前结果与选择；实际条件变化时递增查询版本，清理旧选择、旧行操作资格及旧任务。
3. 空条件立即恢复完整视图，无需等待防抖；仍要使上一轮后台结果失效。
4. 数据未完成加载时保存关键词，等待详情完成。数据就绪时合并约 100 ms 内的连续输入。
5. 到期后后台筛选，仅捕获索引 `Arc`、查询词、完整归属标记和取消标记；不捕获或复制完整歌曲列表。
6. 完成消息通过版本检查后替换匹配索引、结果数量和就绪状态，列表滚动到结果顶部。
7. 内部任务失败显示可重试的筛选失败状态，不伪装成零匹配，也不破坏完整歌单数据。

取消 `JoinHandle` 或丢弃 `spawn_blocking` 的等待句柄不会终止已经开始的阻塞任务。索引构建与筛选必须增加协作取消标记，分批检查；任务所属状态失效或等待任务被取消时通过守卫设置标记。每个歌单搜索只保留最新任务，过时任务尽快退出，不为每次按键积压完整计算。

### 5.4 导航、刷新与滚动

- 首次进入搜索时记录完整列表的滚动位置。实际查询变化清理光标、多选和范围锚点，并回到结果顶部。
- 清除查询前捕获最近定位条目。完整视图恢复后，若该原始条目仍属于同一快照，则定位该条目；没有定位条目时恢复搜索前位置，并按列表长度限制滚动范围。
- 清除不会自动创建批量选择；可以恢复普通列表光标用于继续键盘导航。
- 临时进入正在播放页、队列或设置再返回，保留同一歌单的关键词和结果滚动状态。播放歌曲变化不改变搜索条件。
- 打开另一歌单、重新打开歌单或切换音乐源时重置搜索输入与相关列表滚动状态；A→B→A 不复用第一轮 A 的结果。
- 刷新同一歌单时保留关键词，取消旧筛选。新快照接受后重新搜索并清理旧选择，旧原始索引不能跨快照用于恢复定位；首版回到新结果顶部。
- 移除条目后的刷新采用同一规则，不通过歌曲 ID 推断重复条目的新位置。
- 关闭页面所属状态或程序退出时取消任务；UI 更新不得访问已经失效的实体。

## 6. 显示索引、播放与编辑

### 6.1 借用视图

为 `SongList` 增加类似 `Indexed { songs: &[Song], indices: &[usize] }` 的变体，以及 `original_index(visible_index)` 方法。`get`、`iter`、`len` 与索引访问按映射读取完整歌曲，映射保持有序、有效、无重复位置。

`songs_for_scope(PlaylistDetail)` 返回当前可见投影，供表格、封面预取、光标、多选范围、全选、批量收藏及批量加入使用。`PlaylistLibrary::songs()` 继续返回完整原歌单，供头部统计、完整播放和编辑验证使用。

渲染回调、滚动封面预取与结果数量必须使用同一份已接受投影。仅在明确播放、菜单快照或批量动作边界复制必要歌曲/ID。

### 6.2 单曲与全部操作

`AppState::song_playback_at` 对歌单作用域单独处理：先将可见索引映射成原始索引，再使用完整歌单生成队列替换计划，保留 `QueueOrigin::Playlist`。

头部当前调用 `play_song_at_scope(PlaylistDetail, 0)` 和 `append_songs_at_scope(PlaylistDetail)`。加入投影后，这两处必须改为显式完整歌单操作，例如 `play_playlist_all()`、`append_playlist_all()`，避免搜索后把“全部”错误解释为第一条结果或结果子集。

多选播放、下一首播放、加入队列、收藏与添加到其他歌单，继续读取可见投影的选择集合。只有单曲与头部全部操作使用完整歌单，不能把所有作用域操作统一重定向到完整列表。

示例：原歌单 `[A, B, A, C]` 搜索 A 得到原始索引 `[0, 2]`。点击第二条 A 后完整队列仍为 `[A, B, A, C]`，当前位置为 2；Ctrl+A 后批量播放队列为 `[A, A]`。

### 6.3 菜单与条目身份

歌单行事件需保存音乐源/歌单归属、快照版本、查询版本和原始索引。解析事件时确认快照和可见视图仍有效，并重新定位可见索引；旧查询或旧快照的点击不应落到更新后的同一显示行。

当前 `SongMenuContext` 为普通列表保存整个作用域列表和索引。歌单菜单应在打开时保存完整原歌单快照、映射后的原始索引和完整归属标记。菜单中的“立即播放”、移除确认与 `expected` 顺序验证都基于这份完整快照，不能使用过滤后的 ID 集合。

- 移除确认仍显示原歌单序号，删除指定出现位置。服务端已有完整顺序校验继续保留。
- 执行歌单菜单或确认动作前验证来源、歌单与快照归属；切换来源或刷新后旧动作失效，不改写另一张歌单。
- 非空有效查询期间禁用上移/下移，说明“清除搜索后调整顺序”。仅空格等空查询允许现有排序操作。
- 共享歌单仍按所有者权限决定编辑能力；Bilibili 收藏夹继续只读。
- 收藏、下一首与加入队列根据所指向的歌曲执行，重复歌单条目不被自动折叠。

## 7. 文案与可访问性

新增文案同步写入 `locales/en.yml`、`zh-CN.yml`、`zh-TW.yml`，覆盖普通歌单/Bilibili 占位文案、搜索框名称、清除搜索、匹配数量、无匹配、筛选中、失败重试和调整顺序提示。

歌名、歌手、专辑及来源元数据保持原文。结果数量和忙碌反馈采用页内状态；搜索失败不影响播放器，也不产生音乐源掉线提示。

结果更新时输入焦点稳定，Tab 可以到达列表与清除按钮；清除按钮点击后按定义恢复列表焦点和定位。键盘与鼠标动作使用相同的索引映射和版本验证。

## 8. 性能要求

- 详情接受前后台构建索引，输入后只扫描规范化字段与生成索引数组，主线程不重新规范化整张歌单。
- 搜索复杂度约为条目数 × 查询词数 × 字段子串匹配成本。现有 `uniform_list` 继续虚拟化渲染。
- 匹配索引使用共享不可变数据；渲染和滚动不克隆整个索引或歌曲向量。无查询视图不额外分配 N 个索引。
- 快速连续输入、清除、切歌单与刷新均需协作取消，禁止过时任务堆积。
- 使用 1000 和 10000 条完整元数据的歌单进行压测，记录硬件、构建模式、索引构建耗时和输入到结果的耗时。万条歌单输入到最新结果目标在 200 ms 左右，包含约 100 ms 输入合并等待；实际结果以测量记录为准。
- 不在常规单元测试中使用紧张的机器耗时阈值。单元测试检查取消与数据复制边界，性能用单独可重复的测试或基准记录确认。
