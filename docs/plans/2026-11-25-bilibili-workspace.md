# Bilibili 音源工作区：界面与后续能力方案

日期：2026-11-25。
状态：用户已确认串行开发。第 1 批界面与第 2 批全站搜索、链接/分 P 预览已本地接入。
自动化验证通过；真实站点访问与原生窗口待验收。收藏写入仍未实现，进入第 3 批。

## 1. 当前状态与目标

当前 Bilibili 已提供自己的收藏夹网格、流式详情、分 P 播放、歌单内搜索、来源隔离的队列/历史、歌词与播放资源恢复。它不是没有网格，而是导航和 Provider 能力仍围绕只读收藏夹。

源码边界：

- `src/app/shell/sidebar.rs` 对 Bilibili 使用独立分支；此前在 56px 折叠栏仍显示完整账号名，并始终使用 12px 内边距，导致文字竖向换行、图标空间偏小。
- `src/models/source.rs` 的 Bilibili `search` 已开启，`favorite_write`、`playlist_write` 仍为 false。
- `src/source/queries.rs` 提供独立的类型化视频搜索/详情边界，不将视频候选伪装成已解析歌曲。
  通用曲库搜索及歌单写入仍使用 OpenSubsonic；Bilibili 的结果仅在预览分 P 后显式加入播放链路。
- 收藏夹摘要当前只保存 ID、标题和视频数。封面、描述、公开/私密等展示须先验证接口是否提供，不凭空补元数据，也不为封面加载整张收藏夹。

目标是一个面向听音乐的 Bilibili 工作区，而不是完整视频客户端。维持现有暖白/暖黑、玫瑰品牌色和原生组件，不引入另一套播放引擎或 WebView。

## 3. 建议的信息架构

相关能力实现后，Bilibili 只保留三个一级入口：

```text
首页
收藏夹
搜索

底部：当前账号 / 来源管理 / 折叠开关
```

折叠后仅显示图标，标签放入 tooltip，不把收藏夹名称或账号名压进图标栏。
第 2 批已开放搜索入口：首页/正在播放页 Ctrl+F 聚焦 Bilibili 全站搜索；收藏夹集合页
仍聚焦本地名称搜索，详情页仍聚焦歌单内搜索。三个范围不能混为一个接口。

### 首页：快速开始听

首页以本地内容为基础：继续聆听、最近播放、最近访问的收藏夹。最多保留一项主要开始播放动作和短预览，不复制 Navidrome 的每日推荐或艺术家/专辑模块。

历史须按正在浏览的 Bilibili 账号来源隔离。当前播放来源可能是另一台 Navidrome，因此不能直接把当前播放的 `ListeningHistory` 当成 Bilibili 首页历史。

### 收藏夹：浏览和整理

收藏夹集合页提供搜索收藏夹名称、刷新和明确的加载/错误/空状态。优先用接口提供的封面、标题、视频数；有可靠数据时再展示可见性和描述。

Bilibili 视频封面采用适合 16:9 缩略图的内容卡片；收藏夹与单个视频的数量维度分开。详情继续区分视频及其分 P，不把已加载分 P 数当成总视频数。歌曲表格继续虚拟化并复用已完成的本地搜索。

收藏管理通过卡片/详情的更多菜单进入，不在所有卡片上堆叠删除等按钮。

### 搜索：Bilibili 全站视频，不是当前收藏夹筛选

查询由用户显式提交（Enter 或搜索按钮），结果支持分页和重试，不逐按键发出站点请求。展示视频标题、UP 主、缩略图和时长；分 P 数以实际详情为准。

搜索返回的是视频候选，不是已解析的音频歌曲。点播时再加载该视频的分 P 和可访问独立音轨；多 P 可选一首或播放全部。视频存在不代表拥有可用 AAC-LC 音频，不能先承诺播放成功。

增加 BV/AV 或官方视频链接入口作为补充。短链接解析限制官方域名，解析外部地址时不携带账号 Cookie，不把用户任意 URL 当成可带凭据请求的地址。

搜索标题的站点高亮标签要解析为安全的纯文本，不能直接显示原始 HTML。保留当前独立音轨权限、AAC-LC 解码、地区/删除/会员限制和有界重试语义。

## 4. 收藏写入的范围和安全边界

网站本身支持搜索和收藏管理，但现有客户端还未实现这些操作。站点接口返回成功不等于已确认适用于第三方客户端的使用/分发条件；开始接入前应验证当前请求、会话权限与接口条件。

第一版建议按下列顺序实施：

1. 向自己的收藏夹添加视频、从当前收藏夹移除视频。
2. 创建收藏夹、修改名称/描述和可见性（以已验证权限为限）。
3. 视频复制/移动至另一收藏夹；先确认添加成功，再决定是否移除原收藏。
4. 删除收藏夹等破坏性操作单独确认，明确不删除视频原稿。

写入必须满足：

- 登录 Cookie 继续只从安全凭据会话读取；必要 CSRF 字段按当前接口验证获取，不写配置、日志或界面，不绕过权限/验证码/风控。
- 目标必须是同一已验证账号自己的收藏夹。UI 选择、请求、完成结果同时绑定来源、账号和目标身份，不能在切换账号后应用旧操作。
- 收藏的资源单位是视频身份（BV/AV），不是音频分 P 的 cid 或歌单显示行号。移除一个视频时应明确该视频的所有分 P 都会离开收藏夹，不能删除另一条重复出现的显示行。
- 超时和断连可能意味着写入结果不确定。不能盲目自动重试或展示假成功；先刷新/核对服务端状态，保留局部失败与重新登录入口。
- 编辑收藏不默认停止正在播放的音频。刷新收藏夹后作废旧搜索投影和菜单，队列和历史仍保持来源隔离。

不直接复用 Navidrome 的 `FavoriteKey` 或按歌曲序号的 `PlaylistEdit::Move` 作为 Bilibili 写入协议。先定义 Bilibili 视频/收藏夹领域操作，再判断适合接到哪些通用 capability；排序、批量移动和上传不在接口未验证时开放。

## 5. 实施顺序与验收

| 批次 | 范围 | 当前状态 |
| --- | --- | --- |
| A | 侧栏修复、工作区布局、收藏夹展示 | 首页/收藏夹已本地实现，原生界面待验收 |
| B | 搜索和官方链接 → 视频详情/分 P → 现有播放链路 | 本地实现及契约测试通过，真实站点/原生窗口待验收 |

原估算以熟悉项目的单人开发、接口验证通过且包含单元测试为前提：A 约 2–3 个开发日，B 约 3–5 个开发日，C 的基础操作约 3–5 个开发日。站点限制或分发条件不明确时先暂停相应接口接入，不承诺日期。

每批验证来源/账号切换、迟到响应、加载取消、只读/失效权限、空结果、重复视频和分 P、限流、窄窗口与三种语言。网络契约测试使用本地固定响应；真实账户写入验收必须由用户明确选择测试收藏夹并确认，不能拿现有收藏静默试写。

本方案不包含首页云推荐、视频画面、永久下载、上传、点赞/投币、动态或全站浏览器。

### 第 2 批实施与验证

- 显式提交关键词后，使用固定 API 来源的账号 nav 响应取得 WBI 图像键并验证账号；
  对视频搜索请求签名。一次搜索最多两个账号 API 请求，结果以分页替换；最多浏览 100 页。
  站点高亮标签转纯文本，缩略图只允许图片 CDN；输入/结果/元数据长度都有上限。

  不自动跟随跳转，只接受官方视频/短链目标，最多三个跳转，拒绝用户信息、非标准端口、
  外部域名与重复分 P 参数。AV 详情再次验证 aid，BV 详情再次验证 bvid。
- 搜索/视频预览各自拥有可取消任务，完成时检查来源、请求和快照；新查询或账号切换

- 本地契约测试覆盖 WBI 公共签名样例、来源/账号检查、页码、空结果、异常时长、
  HTTP 412/429 和业务限流、无 Cookie 短链、外部跳转拒绝、错误视频身份和取消竞争。
  三语目录、原有音频/收藏读取回归也纳入完整验证。
