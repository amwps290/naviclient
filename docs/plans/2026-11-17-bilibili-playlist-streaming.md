# Bilibili 大收藏夹流式加载方案

日期：2026-11-17。状态：首版已实现，已完成本地回归与构建验证。

目标：打开大收藏夹时立即展示加载状态，尽早显示第一批已解析歌曲，后续条目按收藏夹顺序追加。完整加载和部分预览具有明确边界。

## 改动前的问题与证据

改动前的加载链路为：

```text
打开收藏夹 → 清空详情歌曲 → 校验收藏夹归属
→ 拉完所有收藏夹分页 → 获取所有视频的分 P 信息
→ 返回完整 PlaylistDetails → 一次性展示歌曲
```

- `src/app/playlists/library.rs::select` 创建空的歌曲数组，每次重新打开都重新请求详情。
- `src/source/bilibili/library.rs::favorite_tracks` 每页获取 20 个视频，先遍历完所有分页，再解析视频详情。
- 视频详情已有 4 路并发，但每组 4 个任务全部结束后才处理结果，再启动下一组。一个慢请求会拖住这一组。
- `src/app/playlists/loading.rs` 只发送一次最终的 `Msg::PlaylistSongs`，加载期间 UI 收不到歌曲。
- `src/app/songs/view.rs` 已采用 `uniform_list`，只渲染可见行；但它将加载中的空数组也展示成“No tracks here yet”。详情头部同时显示 0 首。
- 请求超时上限是 20 秒。临时失败会终止完整加载，即使此前已经解析出歌曲，界面也收不到它们。

因此已经具备服务端分页，缺少的是分页、视频解析与界面之间的增量交付。仅增加显示行数、刷新次数或并发数，无法解除全量结果对首批展示的阻塞。

按 1000 个有效收藏视频估算，当前一次完整加载约需 1 次归属校验、50 次分页请求和 1000 次视频详情请求。实际收藏夹规模及耗时尚未测量，这个数字仅用于说明请求量。

## 推荐的首版行为

| 状态 | 展示与操作 |
| --- | --- |
| 第一批数据到达前 | 保留收藏夹标题，显示加载提示和固定高度的歌曲占位行；不显示“空收藏夹”或“0 首” |
| 已有部分歌曲 | 显示已解析歌曲，提示“正在加载 · 已显示 128 首”；持续追加，用户可浏览和滚动 |
| 全部加载完成 | 使用实际分 P 条目数显示总歌曲数，恢复完整列表的播放与批量操作 |
| 第一批到达前失败 | 显示具体错误和重试入口 |
| 中途失败 | 保留已显示的预览，提示“加载未完成”并提供重试；不将预览标为完整收藏夹 |
| 完整遍历后确实为空 | 显示空收藏夹状态；若全部条目均不可用，显示相应原因与数量 |

收藏夹摘要的 `media_count` 是视频数，展开分 P 后的歌曲数可能不同。加载中不使用“已加载歌曲数 / media_count”计算百分比，也不根据摘要数量决定加载完成。

首版保留当前整收藏夹播放语义：加载期间，顶部“全部播放/全部加入”、歌曲行播放与双击、菜单“立即播放”、键盘 Enter，以及列表批量队列操作统一等待完整加载。当前行播放会把整个列表复制进队列，不能仅禁用顶部按钮。只处理指定单曲的菜单操作可单独判断完整的歌曲身份后使用。

若需要加载期间立即播放，后续应明确设计“仅播放这一首”或独立的队列续载任务；不能直接把不断增长的预览数组当作完整播放队列。

## 加载流程

```text
校验收藏夹归属
  ↓
获取并校验当前页
  ↓
按收藏顺序解析视频详情（并发上限 4）
  ↓
将已完成的连续前缀按分 P 顺序交付 UI
  ↓
继续下一页 → 继续追加
  ↓
所有分页与视频解析完成 → 发布完成状态
```

1. 将视频解析移到分页遍历过程中。第一批可用歌曲的交付不依赖第 2 页及后续页面完成。
2. 使用持续工作的有序并发窗口替代固定分组等待。按序交付结果；已完成但等待前序的结果也计入窗口预算，避免一个慢视频积累大量待发布数据。
3. 视频详情中的 `cid`、分 P 顺序和元数据校验成功后才生成歌曲。保持当前 BV 去重规则处理分页重叠，每个视频内保持分 P 顺序。
4. 第一批可用结果立即发送，之后按条目数或短时间窗口合并更新。建议以 128 条/批、50–100 ms 为调优起点；等待下一次网络响应时，定时刷新仍需有效。
5. 一次加载使用专用的有界更新通道。UI 每轮限量接收并追加，剩余更新留到下一轮，避免无界消息堆积。现有主消息通道若用于唤醒，只发送合并后的更新通知。
6. 首版按页顺序处理即可；后续可评估解析当前页时最多预取下一页。首批展示不需要扩大并发或一次预取所有分页。

首批数据的关键路径从“所有分页 + 所有视频详情”缩短为“归属校验 + 第一页 + 首个可按序发布的视频详情”。若前面的条目不可用或请求很慢，仍需继续等待；占位状态负责这段反馈。

## 数据与应用接入

建议在来源查询边界提供 `PlaylistUpdate`，包括元数据、歌曲批次、进度、完成和失败。Bilibili 协议类型留在 Provider 内，应用只接收通用歌单更新。失败保留错误种类，以区分网络失败、授权失效和账号不匹配。

现有完整详情 API 可作为收集增量结果的封装继续保留。流式路径的完成消息只确认最终状态与统计，不再重复发送、复制一份完整歌曲数组。

| 位置 | 主要改动 |
| --- | --- |
| `src/source/bilibili/library.rs` | 分页内解析、有序并发窗口、批次交付和完整性判断 |
| `src/source/queries.rs`、`src/playlist.rs` | 来源适配和增量更新类型；每批歌曲携带正确来源身份 |
| `src/app/playlists/library.rs` | 当前请求、加载预览、完整状态、错误与取消任务的统一管理 |
| `src/app/playlists/loading.rs` | 接收增量结果、校验请求、触发封面加载 |
| `src/app/shell/polling.rs`、必要的消息处理 | 在现有 50 ms 后台轮询中限量接收更新；加载变化触发重绘 |
| `src/app/library/detail_view.rs`、`src/app/songs/view.rs` | 正确区分加载、部分结果、失败与真正空列表 |
| `src/app/songs/playback.rs`、`row_actions.rs`、`menu.rs`、快捷键分发 | 完整性检查覆盖所有队列入口，校验旧行和旧菜单的归属 |

## 顺序、取消与失败边界

- 沿用 `LibraryRequest`。批次和最终消息都必须属于当前请求、当前来源与收藏夹；切换收藏夹、账号或重新刷新后拒收旧结果。
- 取消需要同时停止分页请求、视频详情任务和待发送更新。保留当前 `JoinSet` 随任务结束取消子任务的能力。
- 同一次加载只向尾部追加，不重新排序已有行；追加时保持滚动位置。打开另一收藏夹时重置其列表位置。
- 行事件和菜单额外绑定收藏夹及加载代次，避免同一 Bilibili 来源内切换收藏夹后，旧索引操作新列表。
- 已删除、地域限制等已知不可用视频继续跳过并累计数量；网络、超时、限流与无效分页令本次加载失败，部分数据仍是预览。
- 重试创建新请求，从第一页重新遍历；新结果替换上一轮预览，不在旧预览末尾重复追加。授权失效或账号不匹配时清除对应预览。
- 完成条件是遇到 `has_more=false` 且此前所有已接收页面中的视频处理完毕。不能用“已达到 media_count”或“通道已关闭”代替完成确认。
- 保留当前每页 20 条、最多 1000 页、最多 100000 个分 P、分页重复检测和账号归属校验。遇到限制不能将已加载部分标为完整。
- 封面继续独立加载，只预取可见范围附近的图片；歌曲显示不等待封面，每次追加也不重复遍历和预取整张列表。

Bilibili 分页缺少本次遍历的固定快照，加载中收藏夹仍可能被外部修改。有序展示、分页去重和完成确认沿用现有遍历语义，不能保证服务器上的瞬时原子快照。

## 后续优化与已有草稿

首版完成增量展示后，再评估有容量上限的完整详情缓存及视频元数据缓存，以改善重新打开和减少重复详情请求。缓存按来源、账号和收藏夹隔离，只有成功完整加载的结果可作为完整快照保存。

当前歌单搜索方案和未接入的 `search_index.rs`、`search_state.rs` 草稿依赖完整详情。后续接入时，首批展示不能等待整张歌单搜索索引构建；首版搜索可在完整加载后启用。本方案不同时扩展搜索功能。

## 实现时的验证

- 本地模拟第一页很快、后续页长期未完成：第一批歌曲必须已进入 UI；加载前和加载中不出现空列表提示。
- 模拟视频详情乱序和慢请求：歌曲始终按视频顺序、分 P 顺序显示，等待发布的数据与请求并发均有上限。
- 覆盖空页、重复页、失效视频、全部不可用、限流、超时、超限和中途失败；只有成功终止的遍历可启用完整队列操作。
- 部分加载时测试顶部按钮、行播放、双击、菜单、快捷键和多选入口；完整加载后与现有队列内容及顺序一致。
- 快速切换 A/B 收藏夹、刷新和切账号：旧批次、完成消息、行事件和菜单不能作用于新列表；取消后没有持续请求。
- GPUI 验证批次追加后的滚动位置、加载提示、失败重试，以及大量分 P 下可见行渲染和更新耗时。
- 分别记录归属校验、分页、视频解析、首批交付、UI 接收、首行绘制及全部完成的耗时，并记录请求数和峰值待发布条目数。先使用本地固定延迟数据比较，再观察实际大收藏夹；不预先承诺固定秒数。

## 已实现的首版

- Bilibili 按页获取并解析视频；使用 4 个有序窗口槽位，已完成但等待前序的视频也占用槽位。第一批可用歌曲立即发布，后续最多 128 首一批，等待视频详情时以 100 ms 定时器刷新缓冲。
- 每次详情请求使用容量为 4 的专用更新通道，发布元数据、歌曲批次、进度与明确的完成或失败事件。UI 在原有 50 ms 轮询中每轮最多处理 16 个更新，并在达到 4 ms 预算后让出下一轮。
- 部分结果只作为预览；重试保留旧预览到第一批新歌曲到达，再替换前缀。空结果完成时也会替换旧歌曲；新前缀采用本轮的封面，授权失败清除预览。切换、刷新与状态销毁会关闭通道并取消任务。
- 顶部、歌曲行、双击、Enter、菜单和多选的列表队列入口统一检查完整性。预览菜单只保存指定单曲，不保留部分列表的队列副本；旧行和菜单按加载快照验证，追加同一快照时仍有效。
- 加载前显示骨架行，加载中显示已加载歌曲数，错误提供实际可点击的重试入口。状态行固定高度，长提示可悬停查看，避免完成提示换行推动表格；封面按收藏夹的可见范围独立请求。
