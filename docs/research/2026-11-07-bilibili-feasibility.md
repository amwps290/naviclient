# Bilibili 独立音轨与音质调研

日期：2026-11-07。关联计划：[Bilibili 音源接入计划](../superpowers/plans/2026-11-07-bilibili-source.md)。

## 结论

Bilibili 的视频清晰度与独立音轨是不同的数据维度。公开视频可以返回多档独立 AAC 音轨，并非只存在视频分辨率选项。本次样本中，调整请求的视频清晰度没有改变返回的音轨集合。

官方大会员页面明确介绍杜比音效权益；维护中的 yt-dlp 提取器也分别处理普通音轨、杜比音轨和 FLAC 音轨。两条本次免登录样本都没有提供杜比或 FLAC 音轨，因此不能从这些样本推断所有内容的最高音质、会员账号可用音轨或 FLAC 的普遍可用性。

初次调研验证了独立音轨元数据；后续已临时获取样本 B 的两条独立音轨并验证 Range。使用项目当前编译的 Rodio/Symphonia 对 AAC-LC 音轨完成约 212.3 秒 PCM 解码，并成功向前、向后跳转。用户实际扫码后，网站 Cookie 会话、账号身份、自己的收藏夹列表、内容首页以及收藏视频的音轨元数据也已验证。没有请求视频媒体数据，后续通过应用 HTTP reader 和异步解码线程的本地样本验证，仍未接通实际音频输出设备。授权失效、完整应用播放与接口使用条件仍待验证，阶段 0 尚未完成。

## 1. 实测范围与方法

- 音质与音轨字节验证使用两个匿名公开视频；随后通过用户扫码建立临时登录会话，验证个人收藏夹，Cookie 不落盘。
- 获取视频元数据，再根据 bvid/cid 请求播放资源元数据。
- 仅记录业务状态、音轨 ID、编码、申报带宽和视频清晰度字段。
- 不将完整签名 URL 或认证信息写入仓库、日志或用户输出，也不下载视频媒体数据。调研完整播放响应和音频样本仅临时保留在 `/tmp`，包含资源地址的文件限制访问权限；登录验证会话仅保留进程内存。
- 对一个样本请求两个视频清晰度值，比较音轨集合。
- 用户提供了 `172.16.15.251:7890` 代理；部分网页、音轨字节和扫码接口验证通过逐请求代理进行，未改变应用或系统网络配置。

下列码率是播放响应中的 `bandwidth`（bit/s）折算值，并非对已下载音频计算出的实际平均码率。不能把一个档位固定标注成所有视频都相同的码率。

### 样本 B：BV1GJ411x7h7

- 标题：【官方 MV】Never Gonna Give You Up - Rick Astley。
- cid：137649199。
- 视频时长：213 秒。

| 音轨 ID | 编码 | 接口申报带宽 | 折算 |

这证明本样本的音轨集合没有随请求的视频清晰度变化。不能把视频质量参数当作独立音轨选择结果。

没有返回可用 FLAC 或杜比音轨。

## 3. 官网与客户端证据

### Bilibili 官方大会员页面

[官方页面](https://big.bilibili.com/)的页面描述包含：

> 更有4K、杜比音效视听特权

这确认官方存在区别于视频分辨率的音效权益。它不证明每个视频都提供杜比音轨，也不能代替实际账号权限和内容验证。

页面引用的[官方播放器资源](https://s1.hdslb.com/bfs/static/player/main/core.bce44a02.js)包含音频档位选择以及“杜比全景声”“杜比音效”的展示逻辑。本次未从该资源确认 FLAC/Hi-Res 的当前官方权益细则。

### yt-dlp 当前提取器

[Bilibili 提取器](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/bilibili.py#L76)分别处理普通、杜比和 FLAC 独立音轨；音轨的编码和带宽分别来自 `codecs` 与 `bandwidth`。本次读取文件的 Git blob SHA 为 `ca37b79deea868e0fb03698de6f1b28caaca3573`。

这是第三方客户端对音轨结构的支持证据，不是 Bilibili 官方授权说明，也不代表本次样本返回了 FLAC，或当前任意账号都有相应权益。

## 4. 对实现计划的影响

1. 保留用户已选择的首版账号登录，不将该选择等同于只播放无损。
2. 不设置“只有高分辨率视频才可播放”的限制；按选中 cid 的独立音轨工作。
3. 不采用“只有 FLAC 才允许播放”作为默认需求，用户尚未提出这一限制。
4. 先支持经真实解码验证的普通独立音轨，依据编码、音轨档位和申报带宽制定选择规则，不盲目比较不同编码的带宽。
5. FLAC、杜比等作为响应可能提供的独立音轨类型，实际支持取决于内容、账号和解码能力；没有实测前不承诺首版支持。
6. 不展示 1080P/4K 作为音频质量标签，也不从视频标题中的“无损”推断流的编码或来源质量。
7. FLAC 编码本身也不能证明上传素材原本就是无损录音。

## 5. 独立音轨字节、Range 与解码补充

针对样本 B，使用 User-Agent 和 B 站 Referer 请求音频资源。两条音轨的请求结果如下：

| 音轨 | 完整音频字节数 | 前两段 Range | 与完整文件对应字节比较 |
| --- | --- | --- | --- |
| 30280 / AAC-LC | 5,408,198 | HTTP 206，0–131071、131072–262143 | 完全一致，Content-Range 总长度一致 |
| 30216 / HE-AAC | 1,167,163 | HTTP 206，0–131071、131072–262143 | 完全一致，Content-Range 总长度一致 |

两个 CDN 响应均声明 `Accept-Ranges: bytes`，媒体 Content-Type 为 `application/octet-stream`。这证明本次两条资源的分段读取路径，不能推断所有 CDN、全部资源或 URL 刷新后的字节一致性。

解码探针直接链接当前项目 `target/debug/deps` 中编译的 Rodio/Symphonia，使用和项目相同的 gapless、长度与 seekable 设置。先以 `audio/mp4` 提示验证两条文件，再以 CDN 实际返回的 `application/octet-stream` 提示重新验证 AAC-LC，解码样本数和跳转结果一致；格式可通过媒体字节探测。探针解码 PCM，不创建音频输出设备。

| 音轨 | 输出采样率/声道 | PCM 样本数 | 推算解码时长 | 跳转验证 |
| --- | --- | --- | --- | --- |
| 30280 / AAC-LC | 48,000 Hz / 2 | 20,381,696 | 212.309 秒 | 120 秒、15 秒、200 秒均成功，之后能读取一秒 PCM |
| 30216 / HE-AAC | 24,000 Hz / 2 | 10,194,944 | 212.395 秒 | 同上；完整 HE-AAC 支持未通过 |

PCM 均非空且无非有限值。Rodio 对两条文件的 `total_duration()` 均为未知，播放进度需要当前 cid 的时长提示，并可用解码结果补充。

**HE-AAC 限制：** `symphonia-codec-aac 0.5.5` 的 AAC 实现读取扩展配置，但音频 payload 处理中跳过扩展填充；当前 24 kHz 输出不能视为已验证完整 SBR 解码。首版优先采用已验证的 AAC-LC，不把“可以输出 PCM”等同于完整 HE-AAC 音质支持。仅有 HE-AAC 等未完整支持编码的内容需明确显示格式能力限制，后续可单独评估解码器升级。

探针源码及样本位于 `/tmp/naviclient-bilibili-probe.py`、`/tmp/naviclient-bilibili-decode.rs` 与 `/tmp/naviclient-bilibili-audio-*.m4a`；不加入默认测试或发布包。

## 5a. 2026-11-08 应用读取器与异步解码补充

使用已临时获取的样本 B / 30280 AAC-LC 音频，通过本地 HTTP 测试服务复现 `application/octet-stream`、独立音频字节和 Range 响应，运行应用本身的 `HttpRangeReader`、临时缓存与异步 PCM 解码线程。没有重新请求 B 站接口、没有请求视频数据、没有创建实际音频输出设备。

| 起播位置 | 解码 PCM 样本数 | 采样率/声道 | 结果 |
| --- | --- | --- | --- |
| 0 秒 | 20,381,696 | 48,000 Hz / 2 | 完整解码通过 |
| 120 秒 | 8,861,680 | 同上 | 起播、解码至结束通过 |
| 15 秒 | 18,941,680 | 同上 | 向后跳转并解码通过 |
| 200 秒 | 1,181,680 | 同上 | 接近尾部起播通过 |

探针以快于实时的速度消费生产用非阻塞音频源，计数扣除了缓冲等待时注入的静音；输出 PCM 有限且非空。缓存上限为 1 MiB，小于 5,408,198 字节的音频文件，验证了超出临时缓存后仍可按 Range 读取与跳转；测试结束未生成持久音频缓存。

固定测试还验证了请求头在预加载、跳转、断流重试和同域跳转中保留，并且不会进入共享客户端的其他请求；跨域跳转停止。测试发现 reqwest 默认会把 Referer 改写为前一请求地址，已在逐资源客户端关闭自动改写。

仓库保留一个默认忽略、需本地样本的开发探针：

```sh
NAVICLIENT_AUDIO_PROBE_FILE=/tmp/naviclient-bilibili-audio-30280.m4a cargo test --locked -j 8 independent_aac_lc_sample_decodes_and_seeks_via_application_http_reader -- --ignored --nocapture
```

这补齐了应用读取器和解码线程的样本证据，仍不能替代真实 CDN 完整播放、输出设备试听、登录生命周期、临时 URL 失效与刷新验证。

## 6. 扫码登录验证进度

用户选择应用内显示二维码、用 B 站 App 扫码确认。当前已验证：

- 二维码生成接口返回业务状态 0，提供 `account.bilibili.com` 确认链接与轮询键。
- 新生成二维码的轮询返回 `86101`（等待扫码）。
- 过期二维码的轮询返回 `86038`。
- 用户在临时网页中扫码并确认，登录轮询返回成功；携带 Cookie 的账号接口返回已登录和有效账号身份。
- 个人收藏夹列表与第一个非空收藏夹的内容首页均返回业务状态 0，首页返回 20 条，`has_more=true`；这里只实测首页，后续页面读取尚未验证。
- 收藏夹视频的详情和音轨元数据请求均返回业务状态 0，样本为单 P，并返回三档独立 AAC-LC 音轨。
- 会话仅保留验证进程内存，验证结束清除 Cookie；未持久化凭据，未向用户输出账号 ID、收藏夹 ID、标题、Cookie 或签名播放 URL。

登录样本的音轨申报带宽分别为 66,371 / 83,799 / 136,606 bit/s；没有返回 FLAC 或杜比。该样本与先前匿名音乐视频不是同一内容，不能据此判断登录提高或降低了音质，也不能推出当前账号的会员权益。

当前实际验证的网站路径为：

- `passport.bilibili.com/x/passport-login/web/qrcode/generate` 和 `.../poll`。
- `api.bilibili.com/x/web-interface/nav`：核对 Cookie 会话和账号身份。

最初代码检查发现服务器密码凭据 API 仅实现 Windows Credential Manager。2026-11-08 已新增独立的 Bilibili 严格凭据 API：Linux DH 加密 Secret Service 与 Windows Credential Manager，不能使用旧服务器密码的明文回退行为。实际 Linux 凭据库连接及随机假凭据的写入、回读、删除验证通过。

## 8. 2026-11-08 账号代码与安全凭据验证

原生扫码与远程网页登录共用固定来源协议客户端和账号配置事务。HTTP 请求不跟随重定向、逐请求设置敏感 Cookie，响应体限 2 MiB，网络失败和解析错误只返回分类，不带 URL、Cookie 或响应内容。二维码轮询间隔 3 秒、180 秒总期限，可关闭或重新生成。

凭据条目包含来源命名空间、账号 ID 和随机 nonce；普通配置不包含会话 Cookie。配置保存前实际回读凭据，登录身份由账号接口核对。相同账号重新授权保留来源身份，不同账号不能覆盖旧来源。取消正在保存的登录不会中断已开始的系统写入；迟到完成由暂存对象回滚，本机账号移除清理该来源的全部旧条目。系统服务异常或进程被强制终止时，未引用的安全条目可能需要后续清理；不承诺跨系统服务故障的分布式事务原子性。

本地固定响应测试覆盖协议状态、账号不一致、恶意确认域、重定向、头注入、响应大小、异常错误脱敏和取消竞争；真实 Linux 系统凭据库测试已完成假凭据的加密写入/回读/删除。Windows 仅验证独立凭据适配器的目标编译。完整账号扫码保存、重启恢复及原生 UI 实机测试尚待完成。

远程模式显式启动，不在普通应用启动时开启网络监听。入口绑定 `0.0.0.0`，访问路径为临时随机值，返回二维码和脱敏状态；服务最多运行 15 分钟。CLI 在文件日志初始化之前处理，不向普通应用日志写入二维码或网页入口。运行命令见 README。
